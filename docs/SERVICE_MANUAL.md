# Руководство по сервису marking-bm

**Версия документа:** 28.10.2026. **Область:** назначение, архитектура, конфигурация, операции, интеграции, обслуживание, восстановление, риски.  
**Не заменяет ролевые инструкции:** [ОБМ](USER.md), [логист](LOGISTICS.md), [администратор](ADMIN.md).

## 1. Назначение и границы

`marking-bm` обслуживает цикл подготовки маркировки импортной радиоэлектроники: накладная ОБМ → состав PN/GTIN/ТН ВЭД → подбор/эмиссия КМ в СУЗ → PDF этикеток → отметка передачи поставщику → подтверждение нанесения → отчёт в СУЗ/ЧЗ → АТК и RESULT → просмотр логистом → локальное закрытие накладной.

**Не реализованы как самостоятельные подтверждённые события:** физическая сборка груза, передача логисту, перевозка, пересечение границы, ФТС, прибытие или приёмка на складе. Маркировочный цикл сервиса и логистика грузов не тождественны.

`done` у **накладной** в API означает **«Комплект сформирован»** (АТК и RESULT готовы). `done` у **внешней операции** означает её успешно подтверждённый результат; у **АТК** означает сформированный АТК. Отображаемые бизнес-статусы различаются по сущностям. Архив означает локальное закрытие/архивацию, а не физическую доставку.

## 2. Состав системы

| Компонент | Ответственность |
| --- | --- |
| FastAPI (`main.py`) | HTML/JSON API, аутентификация, CSRF, ACL, маршруты и фоновые операции |
| `marking_bm/service.py` | Переходы состояний, расчёт потребности, отчёты, партии, АТК, трансформации и блокировки |
| SQLite WAL (`marking-bm.sqlite3`) | Накладные, КМ, неизменяемые файлы, версии, задания, квитанции, аудит |
| `static/app.js`, `static/workspace.js` | Интерфейс ОБМ, логиста, администратора, пошаговые действия, предупреждения |
| Windows-подписант (`signer/`) | Подписывает задание CAdES с сертификатом КриптоПро/Рутокен на выделенном ПК |
| HTTP-клиенты OMS и True API | Взаимодействие с официальными интерфейсами СУЗ/ГИС МТ |
| `scripts/backup.py` | Транзакционно согласованный backup/restore базы, контроль файлов |

Приложение рассчитано на **один рабочий backend worker** с собственной очередью. Не запускайте несколько независимых экземпляров над одной продуктивной базой или с одним набором уже подписанных заданий.

## 3. Роли и доступ

| Действие | ОБМ | Логист | Администратор |
| --- | --- | --- | --- |
| Создать/изменить накладную | Свои | Нет | Все |
| Заказать КМ, отчёт о нанесении | Свои | Нет | Все |
| Просмотреть общий реестр АТК | Нет | Да | Да |
| Скачать общий ZIP АТК/RESULT | Нет | Да | Да |
| Закрыть готовую накладную в архив | Нет | Да | По соответствующему рабочему сценарию |
| Согласовать трансформацию | Нет | Нет | Да |
| Управлять пользователями, настройками и операциями | Нет | Нет | Да |
| Вернуть остановленную накладную из архива | Нет | Нет | Да |

ОБМ ограничен своими документами серверными проверками. Логист видит АТК и RESULT разных сотрудников, но не их исходные накладные и PDF. Администратор входит по отдельному паролю, независимо от обычной роли.

Пароли сотрудников: индивидуальные, хешируются; первичная установка и сброс через одноразовый код, **дважды** вводимый новый пароль от 8 символов. При смене роли, отключении учётной записи и сбросе пароля сеансы инвалидируются.

## 4. Процессы и состояние

### Накладная

```text
Черновик
   → Заказ / получение КМ
   → Этикетки готовы
   → Ожидает нанесения (сотрудник подтвердил передачу ZIP)
   → Отчёт о нанесении в обработке
   → Отчёт принят
   → Формирование АТК
   → Комплект сформирован (done, ещё не архив)
   → В архиве (archive; закрытие в системе)
```

Существуют дополнительные ветви ошибки PDF, предварительной проверки, остановки, трансформации и переразбивки. **Статус «Комплект сформирован» не означает «Груз сформирован» или «У логиста».** Сборка, физическая передача и перевозка не отмечаются этим сервисом.

При изменении разбивки создаются новые версии PDF; старая версия остаётся аудируемой. Операции с КМ не должны обходить серверные блокировки. После отчёта о нанесении содержание исторического отчёта неизменно.

### Внешняя очередь

`signing → leased → queued → dispatching → submitted → done` описывает подготовку подписи и подтверждённую внешнюю обработку. Возможны `preflight_blocked`, `blocked`, `unknown`, `rejected`, `partial`. Неведомый результат **не** является разрешением на повторную отправку.

В админке:
- «Возобновить локальное задание» применимо лишь к доказанно не отправленной операции.
- «Повторить предпроверку» не равнозначно успешной отправке.
- «Запросить проверку статуса» ставит задачу повторной сверки, а не синхронно подтверждает внешнее состояние.
- «Создать повторный отчёт» допустимо только по проверенным условиям отказа/частичной обработки.
- «Указать ID после сверки ЛК» связывает внешнюю операцию, **не создаёт новую**.

### Операции логиста

Реестр группирует АТК по поставщикам и показывает текущие АТК/RESULT и прежние версии файлов. Выбор ZIP сохраняется при перелистывании, **не более 200 АТК** в одной выгрузке. Скачать файл ≠ закрыть накладную. Кнопка открытия карточки ≠ закрытие; закрытие подтверждается отдельно, изменяя локальное состояние `done → archive`.

## 5. Конфигурация и запуск

**Ubuntu VPS:** Python 3.12, фиксированные зависимости из `requirements-lock.txt`, выделенный пользователь `markingbm`, каталог `/var/lib/marking-bm`, HTTPS reverse proxy. Рекомендуемый установочный путь `/opt/marking-bm`. Подробная установка: [README](../README.md).

Systemd-юнит `deploy/marking-bm.service` запускает один процесс на `127.0.0.1:8030`. Наружу этот порт не публикуют; прокси обслуживает корпоративный HTTPS.

Основные параметры в защищённом файле `/etc/marking-bm.env` (см. `.env.example`):
- `BM_DATA_DIR`: постоянное хранилище данных;
- `BM_PUBLIC_URL`: точный внешний URL приложения;
- `BM_COOKIE_SECURE=1`: защищённые cookies на HTTPS;
- `BM_ADMIN_PASSWORD_HASH`: хеш отдельного пароля администратора, не открытый пароль;
- `BM_SIGNER_TOKEN`, `BM_SIGNER_THUMBPRINT`: отдельная авторизация подписанта и отпечаток сертификата;
- `BM_TRUE_URL`, `BM_OMS_URL`: официальные адреса True API и СУЗ;
- `BM_ALLOW_EXTERNAL_WRITES=0`: исходный безопасный запрет внешних мутаций. **Только после приёмки** включают `1`.

Файл `.env.example` предназначен для `EnvironmentFile`; приложение не читает произвольный `.env` автоматически. Секреты не хранятся в Git. Локальный запуск WSL2 описан в [WSL.md](WSL.md); не допускайте одновременную работу VPS и WSL над скопированной очередью.

Команды контроля на Ubuntu:

```bash
sudo systemctl status marking-bm
sudo journalctl -u marking-bm -n 200 --no-pager
curl -fsS http://127.0.0.1:8030/health
```

Перед сетевой диагностикой отделяйте недоступность самого сервиса от ошибки Windows-подписанта и отказа внешнего API.

## 6. Настройка и диагностика Windows-подписанта

Подписант работает в Windows под пользователем, у которого виден сертификат и доступен Рутокен. Сценарии `Start-Signer.ps1` и `Sign-Payload.vbs` следует брать из **одного коммита**.

Для диагностики используйте параметр `-Diagnose` согласно [SIGNER.md](SIGNER.md). Он не требует внешней оплачиваемой операции. Для боевой работы нужны корректный отпечаток, секрет подключения, локальная CAdES-подпись, доступ к серверу и, при необходимости, штатный PIN/касание.

**«Подписант на связи» не означает, что конкретная операция успешно подписана.** Проверяйте её состояние и ошибки в «Операции». Не обещайте бесконтактную подпись до проверки реального сертификата и политики токена на рабочем ПК.

## 7. Эксплуатация и мониторинг

Ежедневно проверяйте: доступность `/health`, статус службы, heartbeat подписанта, токены True API/СУЗ, очередь со статусами `unknown/blocked`, свободное место и дату последнего backup.

Примеры безопасных действий:
1. **Очередь не движется:** проверьте systemd, соединение с подписантом, сертификат, срок токена, включены ли внешние отправки. Не формируйте дубль платной операции.
2. **КМ получены частично:** дождитесь получения оставшихся блоков; при потерянном ответе используйте только предусмотренное восстановление конкретного блока.
3. **Нет АТК/RESULT:** проверьте статусы отчётов, операции группы поставщика и наличие незавершённых трансформаций. Файл нельзя искусственно считать готовым.
4. **Ошибка PDF:** исправьте состав/PN, сохранив ранее полученные КМ.
5. **Расхождение статусов:** сохраняйте внешний ID, квитанцию, время, версию файлов и точную причину. Не используйте ручной повтор без сверки.

Журнал действий и сохранённые файлы нужны для аудита. КМ и квитанции содержат чувствительную информацию; ограничивайте доступ и передачи дампов БД.

## 8. Резервное копирование

Для онлайн-копии используйте **SQLite Backup API**, не копируйте один файл WAL-БД вручную при работающем приложении.

```bash
sudo -u markingbm /opt/marking-bm/.venv/bin/python \
  /opt/marking-bm/scripts/backup.py \
  /var/lib/marking-bm/marking-bm.sqlite3 \
  /var/lib/marking-bm/backups/backup-YYYYMMDD.sqlite3
```

Скрипт проверит целостность SQLite, внешние ключи и SHA-256 вложенных файлов, создаст JSON-манифест. Копируйте резервную копию и манифест **в отдельное защищённое место**. Храните отдельно секреты `/etc/marking-bm.env` и при необходимости токены сервиса.

**Восстановление:** остановите service и подписант/очередь, сохраните исходную БД и WAL/SHM, используйте `scripts/backup.py SOURCE NEW_DESTINATION --restore`. Скрипт **не перезаписывает существующий файл**. Только после проверки подмените рабочую БД, выставьте владельца и права, запустите одну копию службы, перепроверьте `/health`, токены и зависшие операции. Backup не отменяет уже произошедшую в ЧЗ эмиссию или отчёт.

## 9. Обновления и откат

До обновления: зафиксируйте коммит/версию, выполните backup, остановите сервис, установите зависимости из lock-файла; после запуска проверьте здоровье, права и типовые переходы через UI. При возврате к старому коду **нельзя** игнорировать новые таблицы удержания/остановки; если старая версия не поддерживает схему, нужен согласованный restore её резервной копии плюс сверка внешних операций.

Полный цикл тестов:

```bash
python -m ruff check main.py marking_bm tests --select F
node --check static/app.js
node --check static/workspace.js
python -m pytest -q
python tests/browser_smoke.py
```

Браузерные проверки использовали Chromium с выключенными внешними отправками. Они **не доказывают** доступ конкретной организации к API, юридическую корректность операции, реальный PIN/подпись на Рутокене или печать на производственном принтере. Для первой реальной операции используйте [ACCEPTANCE.md](ACCEPTANCE.md).

## 10. Открытые вопросы и ограничения

1. **[#41](https://github.com/AlexSapronov/marking-bm/issues/41):** автоматическая архивация спустя шесть месяцев может переместить накладную из `done` в `archive` без ручного закрытия логистом. Пока не согласовано иное правило, архив **не доказательство** логистического завершения.
2. **Проверка в рабочей сети:** нужны реальные сертификаты, полномочия организации, подпись, доступ к ЧЗ/СУЗ, печать и интеграция с фактическим бизнес-регламентом.
3. **Граница продукта:** физическая перевозка/ФТС/склад не являются зафиксированными событиями этого сервиса; доработка таких сценариев относится к дальнейшей единой ERP.
4. **История API:** админский обзор возвращает ограниченный срез записей аудита; интерфейсная пагинация действует **только на полученный срез**, а не на всю БД.
