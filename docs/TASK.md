## 1. Назначение и окружение

Приложение автоматизирует цикл закупщика/бренд-менеджера по маркировке импортной радиоэлектронной продукции:

**Создать накладную → загрузить и проверить Excel → использовать свободные КМ и заказать недостающие → получить все КМ → создать PDF по PN и количеству → при необходимости поменять разбивку → передать PDF поставщику → подтвердить нанесение → отправить отдельный отчёт о нанесении по каждой накладной → дождаться успешной обработки → сформировать АТК по поставщику и полному ТН ВЭД → выгрузить два Excel → при необходимости выполнить согласованную трансформацию АТК.**

- Одна собственная организация, настраиваемая в админке (не нужен выбор своего юридического лица в документах).
- Поставщиков много; общий справочник.
- Ubuntu VPS, внутренний контур компании, ориентир около 60 ГБ диска. Деплой через systemd, администратор имеет SSH/root на VPS.
- УКЭП находится **только на физическом Рутокене на Windows-ПК администратора**, где уже установлены работающие КриптоПро, браузерные компоненты и средства ЭДО/ЧЗ. На Windows-ПК нет администраторских прав.
- Операции СУЗ/ГИС МТ должны подписываться централизованно максимально автоматически, пока доступен Windows-подписант; обычным пользователям сертификаты и подписи недоступны.

Предпочитай простой стек, согласованный с донорами: Python/FastAPI, SQLite в WAL-режиме при обоснованной нагрузке (или объясни иное решение), HTML/JS/CSS, httpx, ReportLab/openpyxl, фоновые обработчики задач с восстановлением после рестарта. Без ненужных микросервисов, внешних SaaS и сложного frontend-стека. Визуально сделай аккуратный, контрастный и удобный интерфейс.

## 2. Пользователи, авторизация и доступы

- Пользователей по `username` создаёт/отключает администратор.
- **Обычные сотрудники входят по username без пароля**, поскольку это осознанный процесс во внутреннем контуре.
- Сотрудник видит/редактирует **только документы выбранного username**. Замещение отсутствующего сотрудника выполняется входом под его username; передачи документов между пользователями не нужно.
- Администратор видит все документы и может объединять их при массовом формировании АТК. Обычный сотрудник объединяет только собственные накладные.
- Админка защищается **отдельным паролем**, независимо от username, с серверной сессией, хранением хеша пароля и защитой от перебора. Вход под username администратора сам по себе не открывает админку.
- История сохраняет username, время, действие, изменения; физическое лицо при входе без пароля достоверно установить невозможно, не делай ложных заявлений об обратном.
- Отсутствие пароля у рядовых сотрудников **не означает отсутствие проверки прав на сервере**. Защити API от доступа к чужим документам по ID; админские методы недоступны обычным сессиям.

## 3. Документ накладной и Excel

Создание документа: уникальный внутренний ID, номер накладной, поставщик (выбор с поиском/фильтром из общего справочника или создание нового названием), владелец, даты и статусы. Номер одной накладной не должен приводить к смешению данных разных владельцев/поставщиков. Поиск списка документов по номеру, фильтры по статусу, поставщику, дате; отдельно архив.

Импортируемый Excel: обязательные столбцы в фиксированном формате и порядке:

`PN | GTIN | Кол-во в 1 этикетке | Кол-во этикеток | Код ТН ВЭД`

Требования:

- При создании сначала **черновик** и предпросмотр, никакой немедленной эмиссии после импорта. Отдельная кнопка **«Заказать КМ»**.
- Валидировать пустые поля, длину GTIN (14 цифр, сохранить ведущие нули и при возможности проверить контрольную цифру), PN, положительные целочисленные количества, 10 цифр ТН ВЭД, ошибочные Excel-форматы, дубли, потенциально слишком длинные PN для этикетки. Отображать ошибки конкретных строк.
- Один PN может повторяться с **разным количеством штук в этикетке**, если GTIN тот же.
- Совпадающие строки по **PN + GTIN + количеству в этикетке + ТН ВЭД** автоматически объединять с суммированием количества этикеток.
- **Один PN = один GTIN внутри документа**; конфликт блокирует сохранение некорректных данных/эмиссию.
- **Один GTIN = один ТН ВЭД во всей системе**; при конфликте с общим справочником блокировать операцию. Администратор может исправлять ошибочную привязку через отдельную контролируемую операцию с журналом, не изменяя молча историю оформленных документов.
- Один GTIN может встречаться под разными PN в разных документах, но при обнаружении нового соответствия показывать предупреждение и требовать подтверждения. В PDF использовать PN **актуальной накладной**.
- Пользователь может редактировать состав черновика, удалять строки, добавлять PN вручную с полями Excel. При изменении общего количества товара по PN показать сравнение «было/стало/разница» и потребовать подтверждения. Суммировать количество по всем строкам PN, а не только по одной разбивке.
- Количество единиц товара в строке вычисляется как `штук в этикетке × этикеток`. Сверки и итоговые суммы должны быть точны.
- Создать скачиваемый пустой Excel-шаблон для заполнения по согласованному формату.

## 4. Единый глобальный пул КМ

**Принципиальное требование:** свободные ранее эмитированные КМ одного GTIN используются повторно **между любыми накладными, поставщиками и username**. Нельзя без необходимости оплачивать новую эмиссию.

- Все новые заказы КМ: **тип эмиссии `IMPORT`**, **тип оплаты «По эмиссии»**, соответствующий официальный параметр СУЗ проверить по документации (у донора для оплаты встречается `paymentType: 1`). Оплата по эмиссии выбрана, чтобы не действовал временной срок между эмиссией и отчётом о нанесении для этого способа оплаты.
- Перед эмиссией рассчитывать общую актуальную потребность по GTIN, брать доступные коды из пула, **резервировать их транзакционно**, эмитировать **только дефицит**.
- Свободным для повторного назначения может быть только КМ, реально имеющий статус ЧЗ **`EMITTED`**, не закреплённый за чужой активной операцией/документом/отчётом. Перед повторным назначением/изменением количеств повторно сверять статус в ЧЗ.
- Для каждого кода в БД хранить полную исходную кодовую последовательность **с крипточастью и разделителями**, идентификационную часть, GTIN, серийный номер, исходный заказ/операцию СУЗ, актуальный PN, ТН ВЭД, **актуальное количество AI 30**, текущую накладную/поставщика, состояние резервирования/актуальности, историю назначений, PDF-версии и операции в ЧЗ.
- Не смешивать реальный статус ГИС МТ (`EMITTED`, `APPLIED` и др.) с локальными состояниями («свободен», «зарезервирован», «неактуален», «отчёт в процессе»).
- Перераспределять существующие КМ **между строками одного GTIN**, изменяя назначенный AI 30; старые КМ не перепокупаются ради иной разбивки.
- Если КМ больше не нужен, автоматически снять его с назначения, пометить локально как неактуальный для прежнего документа и вернуть в доступный пул при подтверждённом `EMITTED`. Не удалять исходные коды и историю.
- Если кодов не хватает, создать заказ только на недостающее количество; если позже освободились, повторно использовать при следующих накладных.
- Никогда не назначать один КМ двум активным документам одновременно; защитить это проверками БД/транзакциями даже при конкурентной работе сотрудников и фонового обработчика.
- После успешного отчёта о нанесении статус/назначенное количество не редактировать, КМ не возвращать в пул `EMITTED`.
- Источник актуальной рабочей разбивки по каждому КМ: **последняя сформированная версия этикетки**, подкреплённая неизменяемым снимком назначения в БД. Не определять актуальность по имени скачанного пользователем файла. История прежних PDF и назначений сохраняется; сервер знает, какая версия последняя. Старый PDF, уже скачанный поставщиком, отозвать технически нельзя.

## 5. Эмиссия, получение и PDF-этикетки

- По кнопке «Заказать КМ» зафиксировать снимок заказа, атомарно зарезервировать имеющиеся коды и отправить через СУЗ только недостающие (IMPORT, по эмиссии).
- При работе с СУЗ учитывать асинхронную готовность заказа; хранить внешние order ID/block ID и статусы; получать кодовые последовательности с криптохвостом без потери символов.
- Если из 200 нужных кодов получены 150, показывать «150 / 200», но **не разрешать скачивать/передавать PDF до полной комплектности**. Полученные коды сохранены, повторная эмиссия недостающих без сверки результата запрещена.
- Использовать проверенную генерацию **векторного GS1 DataMatrix 58×40 мм** из `km-split`: логотип ЧЗ, PN без лишнего префикса «Артикул», количество штук, читаемый текст КИ, корректные ASCII 29 / FNC1 и AI 30, полная крипточасть. Учесть сериал **20 символов** и оба поддерживаемых криптоформата из донора. Тестировать реальное декодирование метки.
- Отдельный многостраничный PDF на **уникальную комбинацию PN + количество в этикетке + GTIN**. Каждая страница = одна физическая этикетка. Имя строго вида: `PN - Кол-во - GTIN.pdf`, где «Кол-во» = единиц в **одной** этикетке, а не число этикеток. Защита от недопустимых символов имени файла и коллизий.
- Все PDF одной накладной скачиваются **одним ZIP-архивом**. Внутри сохраняется файловая структура; файлы должны читаться и печататься в масштабе 100%.
- После заказа и **до отчёта о нанесении** разрешить менять состав накладной/упаковочную разбивку через UI. Пересчитать пул, получить доп. КМ при необходимости, переиспользовать EMITTED и пересоздать PDF. Сохранить версии файлов и изменения количеств **по каждому КМ**.
- Если PDF изменился после отметки передачи поставщику, сбросить статус передачи; сотрудник должен повторно отметить отправку актуального архива. Старые PDF сохранять в истории, но не предлагать как актуальные.
- Избыточные коды автоматически возвращаются в глобальный пул, дополнительных ручных подтверждений факта «не нанесён» не требовать (это существующая принятая бизнес-практика). **Однако при несовпадении статуса с EMITTED или уже запущенном отчёте повторное назначение блокировать.**

## 6. Передача поставщику и отчёт о нанесении

- После полной готовности этикеток статус **«Этикетки готовы»**.
- Сотрудник сам отправляет ZIP поставщику вне приложения и вручную нажимает **«Передано поставщику»**. Статус становится «Ожидает нанесения».
- После фактического подтверждения поставщика сотрудник вручную запускает **«Сформировать отчёт о нанесении и АТК»** (одна или несколько выбранных накладных, но только доступных ему).
- **Отдельный отчёт о нанесении на каждую накладную**, а не общий по всей партии; при этом пользователь может запустить их обработку одним действием.
- В отчёт включать только **актуальные** коды конкретной накладной, фиксируя **точный AI 30 по каждому КМ** из последней актуальной версии. Никакого восстановления количества из исходного Excel и никакой подмены одной групповой цифрой.
- Использовать для радиоэлектроники документированный тип/структуру отчёта о нанесении импортных КМ, а не `DIVISIONMARK` из `km-split`.
- Только **подтверждённый окончательный успешный результат и квитанции** дают переход к следующим этапам. Отправка запроса или получение ID отчёта ещё не означает успех.
- Если одна накладная получила ошибку, не возвращать успешно обработанные отчёты в исходное состояние и не отправлять их повторно.

## 7. Формирование АТК и массовые партии

- Сотрудник выбирает **одну или несколько только своих накладных**; администратор имеет право выбирать документы любых пользователей.
- На старте массовой операции зафиксировать точный перечень выбранных накладных и состав актуальных КМ. Группировать по **идентификатору поставщика из справочника**, не по похожести текстовых названий.
- Для **каждого поставщика** обрабатывать накладные независимо от других поставщиков. Если у одного поставщика один отчёт неуспешен или ещё обрабатывается, **не начинать АТК по этой группе до успешного завершения всех её отчётов**; остальные группы продолжать.
- **Сначала все успешные отчёты о нанесении → затем реальное создание АТК через ГИС МТ → затем два Excel**. Генерировать АТК самостоятельно или считать Excel заменой создания АТК в ЧЗ нельзя.
- Внутри поставщика КМ группируются по **полному десятизначному ТН ВЭД**. Для каждого полного ТН ВЭД создаётся отдельный АТК с реальным 25-значным кодом, полученным из ЧЗ (при условии документально подтверждённой доступности/схемы API). Разные PN/GTIN с одним полным ТН ВЭД допустимы внутри общего АТК при соблюдении правил ЧЗ.
- Количество единиц товара, соответствующее АТК, рассчитывается как **сумма AI 30** всех входящих КМ, не как число КМ.
- Специальные правила автоматического деления на 30 000 КМ **не реализовывать**: таких объёмов нет. При подтверждённой ошибке ограничения API показывать ошибку.
- Реально проверить статусы `APPLIED`, допустимые особые состояния, принадлежность КМ организации, отсутствие включения в чужой АТК. Не создавать агрегат при проваленной проверке.
- Сохранять АТК, полный состав вложенных КМ, версии состава, связи с выбранными накладными, кодом ТН ВЭД, операцией API и квитанциями.
- Сотруднику выдать **один комплект из двух Excel на каждого поставщика** (даже если выбрано много накладных):
  1. `АТК-<ПОСТАВЩИК>-<НОМЕРА_НАКЛАДНЫХ>.xlsx` со столбцами `ТН ВЭД | АТК | Количество штук (сумма переменной характеристики)`; при нескольких ТН ВЭД несколько строк АТК;
  2. `RESULT-<ПОСТАВЩИК>-<НОМЕРА_НАКЛАДНЫХ>.xlsx` со столбцами `Полный КМ с крипточастью | PN | Количество штук (AI 30) | ТН ВЭД`, **по одной строке на каждый актуальный КМ**.
- Номера всех накладных включаются в имя файла. Для одного документа только один номер; для многих — перечисление. Учитывать недопустимые символы/длину имени, при вынужденном сокращении сохранять полный состав номеров в метаданных и предусмотреть устойчивую уникальность файлов.
- Историю формирования, ZIP/Excel, состав и доступность повторного скачивания сохранять. Не допускать повторного создания АТК из-за повторного клика или перезапуска.

## 8. Завершённые документы, дополнения и трансформация АТК

- После успешных отчётов и АТК завершённый документ **не редактируется**: PN, GTIN, AI 30, ТН ВЭД, состав нанесённых КМ неизменяемы.
- Разрешить создавать **связанное дополнение** как отдельный рабочий документ, не переписывая завершённый. Новые коды должны пройти собственный надлежащий процесс нанесения до включения в существующий АТК.
- Поддержать **только две трансформации существующего АТК в ЧЗ**: **«Добавить КМ»** и **«Изъять КМ»**. Ни произвольного изменения полей нанесённого кода, ни полного расформирования АТК в первом релизе.
- Сотрудник выбирает АТК, указывает конкретные КМ, полностью готовит заявку и отправляет **на согласование администратору**. До одобрения ничего в ЧЗ не отправлять.
- Для **добавления** доступны только подходящие КМ, **уже зарегистрированные в marking-bm**, из документов **любого сотрудника, но того же поставщика**. Не предусматривать загрузку стороннего Excel и ручной ввод неизвестных КМ.
- При подборе ориентироваться на поставщика документа **фактического нанесения**, а не первоначального заказа КМ, который мог переиспользоваться.
- Проверять `APPLIED`, соответствие ТН ВЭД и прочие текущие ограничения API на агрегирование. Чужие документы раскрывать не нужно: в поиске показывать только минимально необходимые сведения о подходящих КМ.
- Администратор видит конкретную заявку, исходный АТК, список добавляемых/изымаемых КМ и может **одобрить/отклонить с причиной**. **Только после одобрения** операция автоматически подписывается и передаётся через предусмотренный API/механизм.
- Только подтверждённый успешный результат трансформации обновляет текущий состав АТК. Старый состав и прежние Excel хранятся как версии, генерируются новые версии итоговых файлов; должна быть история кто/когда/что согласовал.
- Изъятые КМ по-прежнему `APPLIED`, не возвращаются в пул `EMITTED`; локально получают статус **«Изъят из АТК. Требует проверки»**. Их можно предложить для включения в другой АТК того же поставщика **только после отдельного разрешения администратора**. Одобрение следующей трансформации — отдельное действие.
- Не обещать возможность трансформации, если её запрещает фактический статус АТК/ФТС: проверять ответ ЧЗ и блокировать недоступные операции.

## 9. Подписант, админка и интеграция с ЧЗ

Архитектура строго разделяет **Ubuntu-сервер приложения** и **Windows-ПК администратора с Рутокеном**.

### Подписант

- Создать изолированный компонент «подписант», который запускается **без прав администратора Windows** под учётной записью администратора на его ПК и использует уже установленные КриптоПро/Рутокен.
- Цель — **максимально автоматическая подпись** подготовленных сервером заданий, без участия пользователей приложения. Локальный подписант получает защищённые задания из очереди, подписывает точные неизменяемые байты подходящим сертификатом, возвращает CMS/CAdES в нужном документированном формате; сервер отправляет запросы в ЧЗ.
- Реализовать **технический proof-of-concept**: проверить в реальной среде доступность подписи от user-level компонента, необходимость PIN/касания и поддержку последовательной/фоновой обработки. Не заявлять, что автоматический режим возможен, пока не проверено на реальном Рутокене. Если PIN требуется, задания ждут ввода, PIN не сохраняется и не пересылается на VPS.
- Предпочтительно локальная программа/трей-процесс, работающая без открытой вкладки; если API установки/лицензии запрещает этот путь, допустим браузерный подписант на основе CryptoPro browser plug-in как проверенный запасной способ. Интерфейс управления подписантом при этом **в админке marking-bm**.
- Приватный ключ не извлекать и не переносить на VPS. Не логировать PIN, закрытые ключи, токены и полные криптографические секреты.
- Подписант аутентифицируется **отдельно от обычных username-сессий**, использует защищённый канал, разрешённые типы заданий, ограничение на произвольную подпись и защиту от воспроизведения. Подписывает строго сохранённый неизменяемый payload с хешем и ID операции; никакой возможности произвольной подписи через публичный API.
- Очередь долговечная: при отключении Windows ПК статус «Ожидает подписи», после подключения продолжается с того же места. Не обещать 24/7 выполнение, если ПК выключен.
- Типы заданий: авторизация ГИС МТ/СУЗ, заказ КМ, отчёт о нанесении, создание АТК и согласованная трансформация, если требуются подписи для соответствующих документированных API.

### Админка

Разделы: пользователи; поставщики (переименование/слияние дублей); наша организация/OMS ID/omsConnection/шаблоны/endpoint-адреса; ЧЗ/СУЗ/True API и срок действия токенов; состояние Windows-подписанта и сертификата; очередь подписи и ошибки; журнал внешних операций; заявки на трансформацию; разрешения на повторное включение изъятых КМ; общекорпоративный пул кодов и резервы; документы всех пользователей; место на диске и резервные копии.

Администратор может безопасно выполнять **повторную проверку состояния** запросов, но не должен получать кнопку «Отправить ещё раз» без установления результата предыдущей отправки.

## 10. Статусы и пользовательский сценарий

Основные понятные статусы документа:

1. `Черновик` — загрузка/правка Excel, проверка;
2. `Заказ КМ` — резервирование пула и отправка недостающей эмиссии;
3. `Получение КМ` — ожидание полного комплекта;
4. `Этикетки готовы` — PDF и ZIP полностью подготовлены;
5. `Передано поставщику` / `Ожидает нанесения` — сотрудник вручную отметил фактическую передачу;
6. `Отчёт о нанесении` — ожидает подписи/отправлен/обрабатывается;
7. `Отчёт принят` — есть проверенный успех и квитанции;
8. `Формирование АТК` — выполняется после успеха всех отчётов по выбранной группе поставщика;
9. `Завершён` — АТК и оба Excel доступны;
10. `Архив` — завершён и архивирован по сроку.

Дополнительные **подстатусы**: «Ожидает подписи», «ЧЗ недоступен», «Требует проверки администратором», «Операция отклонена», «Неизвестный результат», «Ошибка формирования PDF». Не смешивать отдельные workflow-статусы с состоянием КМ в ЧЗ и состоянием заявки на трансформацию.

Интерфейс: список документов с фильтрами по статусу, поставщику, поиск по номеру; карточка документа с шапкой, строками, суммами, текущей стадией, понятными действиями, логом событий, ссылками на актуальные и архивные версии файлов. Для групповой обработки: чекбоксы и ясный прогресс отдельно по каждому поставщику/накладной.

## 11. Ошибки, безопасность и восстановление

Критичнейшее требование: **никаких дублирующих эмиссий, отчётов и АТК из-за таймаута, повторного нажатия, рестарта или конкурирующих пользователей**.

- Для мутирующих операций использовать уникальные внутренние ID, идемпотентные переходы состояния, durable outbox/очередь и журнал payload/hash. Сохранять запрос до отправки; после отправки фиксировать внешние идентификаторы и квитанции.
- При сетевом таймауте **отправленной** операции не повторять POST автоматически. Безопасно проверять известные IDs и состояния через read-only методы. Если результат однозначно установить нельзя, статус `Неизвестный результат`, блокировка повтора и задача администратору на ручную сверку с ЛК ЧЗ.
- В случае потери ответа на получение кодов учитывать, что буфер СУЗ может уже быть частично/полностью списан: не вызывать получение вслепую ещё раз; предусмотреть восстановление по документированным механизмам либо остановку с пояснением.
- Вся параллельная работа с глобальным пулом, резервированием и отчётами должна быть транзакционно защищена. Нужны тесты гонок и повторных кликов.
- Любое фактическое внешнее состояние (`EMITTED`, `APPLIED`, состав АТК) перепроверять, а при расхождении не «чинить» локальную базу молча.
- Исключить удаление/перезапись истории КМ, отчётов, составов АТК и одобрений. Скрытие неактуального != аннулирование КМ в ЧЗ.
- Все секреты только во внешней защищённой конфигурации/хранилище, не в Git. Логировать достаточно для диагностики, но не секреты. HTTPS внутри инфраструктуры для чувствительных API/подписанта; CSRF/session/security headers по месту.
- Модель угроз: пользователь может войти под чужим username; это принятой бизнес-практикой не устраняется. Но серверные операции не должны давать доступ к админке/подписанту и не должны позволять злоупотребление прямыми API-запросами.

## 12. Архив и резервное копирование

- **Через 6 месяцев после статуса «Завершён»** автоматически переводить накладную в архив, скрывая из основного рабочего списка. Не удалять документы, КМ, отчёты, PDF, исходные Excel, АТК, RESULT, историю и квитанции.
- Всё должно открываться/скачиваться из архива. Завершённые/архивные сведения неизменяемы, кроме отдельно согласованных дополнений/трансформаций с версионированием.
- Не генерировать ненужные дубли PDF/ZIP при повторном скачивании неизменённой версии; формировать повторно только при изменении снимка данных.
- Резервная копия БД должна быть консистентна с SQLite WAL; вместе с БД сохранять версии файлов и конфигурацию без раскрытия секретов. Дать скрипты backup/restore и **проверку восстановления**. Рекомендовать вынести копии за пределы единственного диска VPS.
- Админке показывать занятое место, свободное место, состояние последнего бэкапа и предупреждения. Автоматической очистки данных не делать.

## 13. Обязательные автотесты и приёмка

Нужны unit, integration (с моками API), браузерные smoke и тесты восстановления состояния, как минимум для следующих случаев:

1. Импорт Excel с корректными строками, объединением одинаковых, повтором PN с разными количествами; ошибки PN→разные GTIN, GTIN→разные ТН ВЭД, глобальный конфликт ТН ВЭД, предупреждение при разных PN одного GTIN.
2. Изменение общего количества в накладной с обязательным подтверждением разницы.
3. Два пользователя одновременно резервируют последние свободные 10 КМ одного GTIN: не появляется двойного назначения.
4. Накладная A заказала 100×5, затем стала 50×10: 50 КМ используются с обновлённым AI 30, 50 возвращаются в пул. В новой накладной поставщика B берутся ранее освобождённые EMITTED, новые не заказываются.
5. Другое соответствие PN для того же GTIN: предупреждение, после подтверждения PDF с PN актуальной накладной.
6. Если статус реального КМ не EMITTED, перенос/правка запрещены. После APPLIED изменение AI 30 и возврат в пул запрещены.
7. Не потерять криптохвост, 20-символьный serial, ASCII GS/FNC1 и AI 30; DataMatrix в PDF читается сканером/декодером; печать строго 58×40 мм. PDF по `PN - Кол-во - GTIN.pdf`, ZIP по накладной.
8. До получения полного комплекта КМ PDF не доступен; 150/200 не приводит к выдаче неполного ZIP.
9. После изменения PDF статус «Передано поставщику» сбрасывается.
10. Массовая обработка 3 накладных поставщика A и 2 поставщика B: пять самостоятельных отчётов; один отчёт A с ошибкой блокирует АТК только A; B получает свой АТК+RESULT; после исправления A уже успешные отчёты не дублируются.
11. Группировка АТК по **полному ТН ВЭД**, суммирование **AI 30**, верная раскладка КМ и два Excel по каждому поставщику с именами и перечнем номеров накладных.
12. Повторное нажатие, таймаут после отправки, рестарт между отправкой и ответом, повторное получение из СУЗ: без слепых дублей и потери кодов.
13. При недоступности Windows-подписанта задания ждут, восстанавливаются после подключения. Обычный сотрудник не может управлять подписью или открывать админку.
14. Трансформация АТК без одобрения не отправляется; выбор добавляемых КМ только из приложения, того же поставщика, допустимого статуса; изъятый APPLIED не попадает в пул; повторное включение требует **двух отдельных решений администратора** (разрешение КМ + одобрение заявки).
15. Архивация после 6 месяцев и повторная загрузка всех файлов, восстановление из бэкапа.

В каждом тесте ясно отличай demo/mock от проверенного live. Сделай отдельный чек-лист первой реальной операции в ЧЗ (под контролем администратора) с шагами отката/остановки при неизвестном результате, чтобы не создавать лишних платных КМ.

## 14. Конечные артефакты

В рабочем репозитории должно быть:

- Исходный код backend/frontend, миграции/инициализация БД, тесты, mock-режим.
- `README.md` с установкой, архитектурой, настройкой ЧЗ/СУЗ и скриншотами/описанием UI.
- `.env.example` без секретов, systemd unit и безопасная инструкция деплоя/обновления на Ubuntu VPS.
- User-level Windows-подписант, инструкция запуска без админских прав, тест соединения, диагностика Рутокена и управление через админку; документированные ограничения фоновой подписи.
- Инструкция для сотрудника по-человечески: создать накладную, загрузить Excel, заказать коды, получить ZIP, передать поставщику, подтвердить нанесение, получить АТК/RESULT, создать заявку на трансформацию.
- Инструкция администратора: пользователи, поставщики, интеграции, подпись, ошибки, согласования, резервные копии.
- Матрица статусов/переходов и модель хранения/резервирования КМ.
- Тесты и инструкция безопасной приёмки на демо, sandbox и продуктиве (отдельно).

**Критерий завершения:** не просто работающий интерфейс, а проверяемый end-to-end процесс с реальными или документированно готовыми к включению интеграциями, воспроизводимыми тестами и строгой защитой от ошибочных/дублирующих операций. Непроверенное явно указать в итоговом отчёте, не маскировать под готовность.

### Важные границы проекта

Не нужно: деление КМ по схеме `DIVISIONMARK` из `km-split`, складское сканирование приёмки/отгрузки, ввод товара в оборот, расформирование АТК, пересоздание/редактирование уже `APPLIED` КМ, дробление АТК на блоки по 30 000, платная новая эмиссия при наличии свободных `EMITTED` того же GTIN, ручная подпись со стороны бренд-менеджеров, автоматическое удаление файлов.
